# 企业 Agent 能力体系观点文写作模式

适用于企业 Agent、AI 治理、数字化转型、工具调用安全、企业能力平台等主题。

## 核心陌生化角度

不要把文章写成“Agent 有哪些安全风险”或“如何开发 Agent”的技术科普。更有信息增量的判断是：

> 企业 Agent 的建设顺序经常反了。Agent 只是能力消费者，企业应先沉淀它能安全调用的能力体系。

关键概念区分：

- API 解决系统如何通信。
- MCP 解决模型如何标准化发现和调用工具。
- Skill 解决特定任务中如何组合知识、规则与工具。
- 企业能力还必须回答身份、授权、对象、上下文、影响范围、审计、补偿和责任归属。

可复述定义：

> 企业能力，是一项经过业务语义封装，并且带着身份、权限、策略、审计和责任边界的可执行动作。

## 推荐递进主线

1. **生产环境冲突**：演示效果很好，安全团队一追问就无法上线。
2. **范式变化**：聊天机器人停留在回答，Agent 会把概率性判断变成确定性动作。
3. **概念纠偏**：API、MCP、Skill 都不自动等于可治理的企业能力。
4. **资产重定义**：从“做多少 Agent”转向“企业有多少可安全复用的能力”。
5. **机制拆解**：能力进入生产需要通过治理门槛。
6. **权力变化**：Agent 是新的非人行动主体，能力治理是在分配数字权力。
7. **冷静边界**：不要造超级大中台，不是所有动作都适合自治。
8. **行动路径**：从真实任务抽取高频能力，用第二个 Agent 验证复用。
9. **升华**：智能来自模型，权力来自组织授权。

案例不能按厂商平行罗列。OWASP、NIST、MCP、AWS、Microsoft 等资料只用于支撑递进链条中的不同论点。

## 能力体系六道门

一项能力进入生产环境，至少检查：

1. **可发现**：业务语义、输入输出、风险等级、版本、负责人清楚。
2. **可识别**：Agent、用户、工具与资源拥有可追踪身份，区分服务身份和用户委托身份。
3. **可授权**：每次调用按主体、动作、对象和上下文动态决策，不能只做一次静态授权。
4. **可约束**：参数、额度、频率、环境、数据去向和风险阈值由确定性规则控制。
5. **可观察**：记录目标、规划、工具、参数、策略决定、业务结果、成本和异常行为。
6. **可干预**：具备审批、暂停、幂等、熔断、补偿、撤销和人工接管。

能力地图可按以下类别组织：信息能力、分析能力、交易能力、沟通能力、控制能力。

## 权威依据的使用方式

优先查官方资料，不引用二手安全营销文章作为核心证据：

- OWASP Excessive Agency：功能过多、权限过大、自治过高。
- OWASP Agentic Top 10：目标劫持、工具误用、身份与权限滥用、级联故障等。
- NIST SP 800-207：零信任适用于用户、应用和其他非人访问主体；访问具体资源前认证与授权。
- MCP Enterprise-Managed Authorization：通过企业 IdP 集中管理 MCP Server 访问和撤权。
- AWS Agentic AI Lens：每次工具调用由外部网关按策略授权，传播身份上下文，高风险写操作人工复核。
- Microsoft Entra Agent ID：Agent 使用专门身份与最小权限，限制高权限角色。

不要把启发式公式冒充权威标准。若使用“风险暴露≈影响面×权限范围×自治程度×不可逆性”，必须明确它是作者用于讨论的非正式框架。

## 可传播金句模板

- 上游是概率世界，下游是责任世界。
- 接口让系统连接，能力让责任闭环。
- Agent 会快速迭代，企业能力应该成为慢变量。
- 不能让 Agent 同时担任申请人、审批人和执行人。
- 让模型负责智能，让确定性系统负责底线。
- 能力只有被第二个场景复用，才开始从项目代码变成企业资产。
- 不要因为 Agent 足够聪明，就给它隐式权力。

## 防止“大中台”误读

提出能力先行后，必须主动划清边界：

- 不先建覆盖全公司的超级平台。
- 不先定义几百项能力再寻找场景。
- 从三到五个真实任务拆出重复动作。
- 优先区分读与写、建议与执行、普通与高风险动作。
- 第一个 Agent 验证项目，第二个 Agent 验证能力复用。

核心判断：规模化不是复制 Agent 代码，而是降低新 Agent 获取合规能力的边际成本。
