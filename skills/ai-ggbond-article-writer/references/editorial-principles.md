# 编辑原则与常见修正模式

## ⭐ 核心论点扣回原则

当文章有明确的核心概念（如"Harness"、"Agent"、"超级个体"）时：

**规则：每个章节、每个子章节都必须与核心概念直接相关。**

### 什么该砍
- 产品介绍性内容（Star 数、安装命令、功能列表、合作伙伴名单）如果不能直接服务于核心论点
- 定价信息（除非文章本身就是价格对比）
- 工具的安装步骤、CLI 命令（除非文章是教程）
- 与核心论点无关的"百科全书"式罗列

### 什么该留
- 直接解释"为什么这个产品/做法体现了核心概念"的内容
- 能让读者理解核心论点的关键架构、设计理念、哲学差异
- 有洞察力的分析和对比

### 判断标准
**"这段内容去掉后，读者是否无法理解核心论点？"**
- 如果答案是"不影响" → 删
- 如果答案是"会少一个支撑论点的论据" → 留

### 实际案例（2026-05-11）
文章《从模型崇拜到 Harness 觉醒》初稿 Google 章节包含了：
- Gemini CLI 的 Star 数、安装命令 → 砍（产品介绍，不扣 Harness）
- ADK 的 Star 数、安装命令、语言支持列表 → 砍（技术文档，不扣 Harness）
- Google AI Studio 功能列表 → 砍（完全不沾 Harness）
- A2A 合作伙伴名单 → 砍（商务合作，不扣 Harness）
- Jules 的异步架构设计 → 留（直接体现"注意力约束"即 Harness）
- ADK 的回调机制和多 Agent 编排 → 留（直接体现 Harness 的约束/编排能力）
- MCP 工具统一层 → 留（直接体现 Harness 的连接层）
- Deep Think 推理分层 → 留（直接体现"按需路由"即 Harness）

用户原话："里面有几个内容看上去与核心论点没有特别大的关系，我只想体现与核心论点有关的内容。"

## 多轮修订处理原则

当用户一次性提出多个修改点时：
1. 逐一确认理解每个修改点
2. 一次性全部修改完成，不要分批
3. 修改完成后逐条汇报改动清单（✅ 表格形式）
4. 主动发送修改后的文件
