# 已确认选题后的文章主体快车道（2026-05-25 会话沉淀）

## 触发场景

用户已经确认了某个选题（例如“选题一 OK”），随后说：

- “按照技能来写文章的主体内容”
- “直接写正文”
- “先写主体内容”
- “这周要改成上周，其他 OK”

此时不要重新做内容类型判断、选题策划或配图确认；进入正文快车道。

## 关键工作流

1. **先恢复已确认选题上下文**
   - 如果当前上下文里缺少“选题一”的具体内容，不要猜。
   - 优先用 `session_search` 搜关键词；如果搜不到，使用 `hermes-session-content-search` 工作流：`hermes sessions export` + Python/grep 检索。
   - 搜索关键词建议：`选题一`、文章标题片段、`公众号文章`、`主体内容`、用户提到的时间口径词（如“这周/上周”）。

2. **尊重用户的局部修正与最终标题口径（⭐重要：最新标题优先）**
   - 用户指出"今天是周一，所以把'这周'改成'上周'"，正文中必须统一时间口径，并在写完后用工具检查：`这周` 计数必须为 0。
   - 但如果后续用户明确给出新的选题/标题且标题里明确写了时间词（例如《GitHub 热榜这周杀疯了：...》），**以用户最新明确标题为准**，不要机械套用上一轮"周一改上周"的规则。
   - 同理，用户局部修正后再次给出完整标题时，应优先信任用户最新标题，再检查全文口径是否与最新标题一致。
   - 趋势文章写完后必须做双向时间口径检查：标题要求"这周"时确认没有误写"上周"；标题要求"上周"时确认没有残留"这周"。

3. **上下文压缩后的主动续写**
   - 如果系统提示“active task list was preserved across context compression”，将其视为当前任务状态，不要重新问用户要上下文；按任务清单继续执行。
   - 若已加载写作技能且用户已确认选题，继续快车道：补 brief/knowledge base → 写 Markdown → 洁净度/素材/时间口径检查 → 以附件路径汇报。

4. **只交付用户当前要求的阶段**
   - 用户只要“主体内容”时：只写 Markdown 正文，不要擅自生成配图、HTML、推送公众号。
   - 可创建标准文章目录、brief、knowledge base，为后续配图/排版留好位置。

4. **文件落地规范**
   - 路径：`/Users/admin/SuperIp/article/YYYYMMDDHHMM-主题/`
   - 至少包含：
     - `_briefs/[主题]-需求brief.md`
     - `_knowledge_base/[主题素材]-日期.md`
     - `YYYYMMDDHHMM-[主题]-主体初稿.md`

5. **GitHub Trending / 热榜文章修订规则**
   - 周一处理“本周/这周热榜”文章时，默认这些项目已经属于上周 GitHub Trending；若用户提醒“今天是周一”，标题和正文统一改为“上周”，并用工具确认 `这周` 计数为 0。
   - 开头先给普通读者补一句 GitHub Trending 科普：它是开源世界热榜/开发者兴趣雷达，不是行业报告，但能提前暴露开发者集体关注方向；再进入榜单项目。
   - 如果文章来自不同 GitHub 项目，每个项目章节末尾必须附“项目链接：”纯文本 URL，避免读者找不到来源，也方便公众号展示。
   - 后半段不要堆解释；收束成更有感召力的行动号召，例如“别再围观了，把 AI 接进你的系统”，用 3-5 个具体自检问题推动读者行动。

6. **正文洁净度自检**
   - 检查不出现：`建议阅读`、`点击右上角`、`全文核心信息图`、`配图：`、`图片说明`、`figcaption`。
   - 检查负向 AI 味词：`深入探讨`、`赋能`、`综上所述`、`总而言之`。

## 回复用户时

简短汇报：文件路径、已完成的时间口径修正、洁净度检查结果、核心判断/金句。不要把全文重新贴进聊天窗口，除非用户明确要求。
