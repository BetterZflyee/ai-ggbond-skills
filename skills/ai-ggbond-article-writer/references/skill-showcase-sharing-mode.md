# 技能展示类文章：分享模式（歸藏模式）

日期：2026-05-29
来源：飞哥写 remove-ai-marks 开源文章时的 3 次纠偏

## 背景

飞哥要写一篇开源 Skill 的公众号文章。Agent 第一次设计了"调查实验型"框架（侦探拆解式），飞哥否了；第二次设计了"故事→产品→设计决策→行业科普"框架，飞哥说"站在普通人分享欲上，不用讲为什么做成这样"。

最终确认的模式参考了两篇文章：
- 歸藏《开源一个 PPT Skill｜压进了我 10 年的设计经验》
- 花叔《达尔文.skill 正式发布：一个无限进化的 Skill 系统》

## 核心原则

**分享欲，不是科普专家。** "我做了个东西，给你看看"，不是"我来给你分析为什么这样设计"。

## 与"调查实验型"的区别

| | 调查实验型（旧） | 分享模式（新） |
|---|---|---|
| 叙事弧 | 发现问题→困惑→拆图→踩坑→解法→卧槽 | 故事引入→产物体验→能做什么→怎么用→开源 |
| 主角 | 人（的实验和发现） | 人（的分享欲） |
| 技术细节 | 作为"顺手掏出"的补充 | 正面介绍功能，但用大白话 |
| 设计决策 | 不讲 | 不讲（飞哥明确砍掉） |
| 行业科普 | 可以有 | 不需要（飞哥明确砍掉） |
| 踩坑经历 | 核心叙事 | 简短带过，不是主干 |

## 文章结构模板

1. **开头故事**（~400字）：一个具体场景引入，自然引出"我做了个东西，开源了"
2. **它长什么样**（~500字）：直观感受，before/after
3. **它能做什么**（~1200字）：核心能力，白话讲，不堆术语
4. **怎么用**（~1500字）：最常见的 3-4 个场景，**用自然语言指令**，不用命令行
5. **用着怎么样**（~800字）：简短踩坑+最终效果
6. **开源**（~400字）：链接、安装、金句收尾

总字数 5000-6000，不注水。

## 关键红线

### 1. 怎么用部分：禁止命令行代码块

飞哥原话："用户看到 python3 scripts/clean.py 就会退场的"

- ❌ `python3 scripts/clean.py 你的图.png --metadata-only`
- ✅ 「帮我清除这张图的AI水印：images/cover.png」
- ✅ 「把 images 文件夹里所有图片的AI元数据清掉」

所有用法必须用自然语言指令（用户对 AI 说的话），不是命令行。

### 2. 不暴露底层依赖

飞哥原话："这不是拆我台吗，暴露了技能不是我原创的"

- ❌ "最后找到了 wiltodelta/remove-ai-watermarks 这个开源库"
- ✅ "折腾了一圈，我决定自己写一个专门干这件事的 Skill"

底层实现来源不提，只说"我写了/我做了"。

### 3. 不讲设计决策

飞哥原话："不用讲为什么做成这样"

砍掉"为什么做成这样"整个章节。不需要解释"为什么基于 XX 库""为什么分三层引擎""为什么做成 Python API"。

### 4. 不做行业科普

砍掉"AI 水印这件事你该知道的"这类行业分析。文章是分享，不是报告。

### 5. 结尾聚焦痛点，不讲大道理

飞哥纠正了结尾：不要讲"水印本身不是坏事""版权保护是正当理由"这种平衡论述。

要讲具体痛点：**平台把溯源信息变成降权信号，塞进推荐算法里，从来没告诉创作者。**

结尾模式：
- 平台在偷偷读标记 → 默默降权 → 你从来没见过任何提示
- 创作者两难：用 AI 被降权，不用 AI 跟不上
- 两头都不说，创作者被闷声收割
- 这个 Skill 把选择权还给你

## 适用场景

当用户说"写一篇关于 XX 技能/工具的文章""开源 XX""介绍 XX Skill"时，优先使用此模式。

如果用户明确要求"调查实验型"或"行业分析型"，则按对应模式执行。
