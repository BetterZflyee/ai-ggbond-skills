# Skill Showcase Article Pattern / 技能展示文章写作模式

> 当文章主题是介绍你自己开发的某个 Skill/工具/项目时使用此模式。

## 两种可用原型（必须问飞哥选择，不可自作主张）

| 原型 | 叙事弧 | 适用场景 | 参考文章 |
|------|--------|----------|----------|
| **歸藏分享型** | 故事引入→产物体验→能做什么→怎么用→用着怎么样→开源 | 飞哥说"科普/介绍/分享"或无明确指示时的**默认选择** | guizang-ppt-skill |
| **调查实验型** | 发现问题→困惑→实验→踩坑→解法→卧槽结果→开源 | 飞哥主动要求"侦探/拆解/实验"叙事 | remove-ai-marks v2 |

**判断方法**：飞哥说"参考歸藏那篇"或"参考这篇文章"+链接 = 歸藏分享型。飞哥说"像侦探一样拆解"或"我替你做了实验" = 调查实验型。**未明确指示时默认歸藏分享型。**

**铁律**：不可自选原型，必须从飞哥的指示中判断。选错原型会导致文章被推倒重写（2026-05-29 实战教训：飞哥要歸藏分享型，我选了调查实验型，被纠偏）。

## 原型一：歸藏分享型（默认）

**核心调性**：站在"普通人分享欲"上——"我发现了一个好东西，给你看看"。不是科普专家分析设计决策，不是技术文档讲解原理。

**参考文章**：
- 歸藏 PPT Skill：mp.weixin.qq.com/s/GXjjlxpIJ604HVCCZJkUBA
- 花叔 达尔文.skill：mp.weixin.qq.com/s/4ICQJGwa2MD616_oFmJb4w

### 结构模板

1. **开头故事**（~400字）：一个具体场景自然引出"我做了个东西，开源了"。不要讲"为什么做"的决策过程，只讲故事本身。
2. **它长什么样**（~500字）：给读者一个直观感受，before/after 效果。"不像AI做的，更像XXX"
3. **它能做什么**（~1200字）：核心能力白话讲，不堆术语。用类比和具象化表达。
4. **怎么用**（~1500字）：场景化介绍，每个场景一段自然语言示例。**禁止命令行代码**（见下方铁律）。
5. **用着怎么样**（~1000字）：真实使用体验、踩坑经历。用故事感讲，不要列清单。
6. **写在最后**（~400字）：开源链接、安装方式、金句收尾。回环呼应开头。

### 歸藏分享型禁区

- ❌ **禁止"为什么做成这样"章节**：飞哥明确拒绝——"站在普通人的分享欲上面，而不是一个科普专家，不用讲为什么做"。不要讲设计决策、不要分析架构选择。
- ❌ **禁止"行业背景/你该知道的事"章节**：不要上升到行业分析，保持"分享好东西"的调性。
- ❌ **禁止设计决策分析**：不要"为什么基于X而不是Y""为什么分三层而不是一个函数"。

## 原型二：调查实验型

**核心调性**：我替你去做了这个实验，发现了什么。英雄之旅弧线。

### 1. 痛点共鸣（300-400字）
- 用具体数字开场（关注了多少人、每天多少条信息、花了多少时间）
- 描述焦虑/低效的真实感受
- 核心：让读者觉得"这说的就是我"

### 1.5（可选）科普铺垫（300-500字）
- **何时需要**：工具解决的问题涉及读者不熟悉的底层机制（如 AI 水印、元数据、协议等）
- 用通俗类比解释技术原理
- 核心：让读者在进入方案之前先理解"问题长什么样"

### 2. 为什么现有方案不行（400-500字）
- 列举2-3个你试过但失败的方案
- 每个方案说清楚"为什么不行"（具体缺陷，不是笼统的"不好用"）
- 核心：为你的方案建立"存在的必要性"

### 3. 我的方案概览（500-600字）
- 用分层/分模块的方式讲清楚架构
- 每一层讲清楚"它解决什么问题"
- 适当暴露技术细节，但不要堆代码
- 核心：让读者理解方案的逻辑，不是要教会他实现

### 4. 实际效果展示（300-400字）
- 用真实数据说话（抓了多少条、分了几个类、省了多少时间）
- 列举2-3个具体的内容示例
- 核心：让读者看到"这东西真的能用"

### 5. 深层认知升华（300-400字）
- 从工具层面拔高到认知/方法论层面
- 提炼出1-2个"金句"级别的观点
- 核心：让文章有转发价值，不只是"又一个工具介绍"

### 6. 技术踩坑记录（300-400字）
- 列举3-5个你实际踩过的坑
- 每个坑说清楚"是什么"+"怎么解决"
- 核心：帮读者少走弯路，同时展示你的专业度

### 7. 开源引导+CTA（200-300字）
- 先给价值（"你只需要做三件事"），再给链接
- 说清楚仓库地址、技能目录、快速上手步骤
- 最后一句可以用"如果觉得有用，欢迎Star ⭐"
- 核心：降低行动门槛，让人真的去试

## 实操案例：remove-ai-marks 文章

2026-05-28 飞哥确认通过的技能展示文章《发图前多一个动作，平台算法就"看不见"你是AI了》（8331字），结构如下：

1. 痛点：朋友178浏览 vs 2400浏览，我自己的五倍实验
2. 科普：三张"身份证"——可见火花 / C2PA 元数据 / SynthID 像素水印
3. 为什么不行：ExifTool（C2PA清不掉）、加噪点（破坏画质）、不用AI（不现实）
4. 方案：ai-ggbond-remove-ai-marks，三层引擎对应三种标记
5. 使用：对话式 / 单张命令行 / 批量管线
6. 认知：不是作弊，是算法黑盒下的合理自卫
7. 踩坑：Python版本冲突、Path/str类型、静默下载、MPS限制、C2PA特殊区块
8. 开源：GitHub链接 + 三步上手

**关键经验**：
- 水印/元数据类的技术问题，科普章节必不可少——读者不先理解"图片里有看不见的标记"，就不会理解"为什么 ExifTool 不够用"
- "不是作弊"章节是价值锚点——读者会有道德犹豫，主动回应这个问题能大幅提升信任和转发

## 写作注意事项

1. **第一人称贯穿全文**：这是"我的实战故事"，不是产品文档
2. **失败案例必须真实**：不要编造"试过X但不行"，用你真正踩过的坑
3. **技术深度适中**：让小白看懂逻辑，让同行看到细节
4. **金句密度**：每800-1000字至少一个可以被划线转发的观点
5. **GitHub链接出现两次**：正文中自然提及一次，结尾CTA再正式列出
6. **不要过度推销**：80%讲价值和故事，20%引导行动
7. **确认正文后再配图**：正文写完后先让用户过目，用户说"确认"再进配图阶段

## ⚠️ Hermes Skill 文章铁律：禁止 CLI 命令，只用自然语言（2026-05-29 飞哥纠偏）

当文章介绍的是 Hermes Agent 的 Skill 时，**用户不需要敲命令**。他们只需要跟 AI 说中文就行。

**❌ 错误示范**（用户看到这些会退场）：
```bash
python3 scripts/clean.py 你的图.png --metadata-only
```

**✅ 正确示范**（自然语言，像跟朋友说话）：
> 帮我清除这张图的AI水印：images/cover.png

**✅ 批量操作也用自然语言**：
> 帮我清除 images 文件夹里所有图片的AI水印

**✅ 询问/诊断也是自然语言**：
> 帮我看看这张图有没有AI标记

**原理**：Skill 的价值就在于"用中文说一句话就能用"。如果文章里展示命令行，读者会觉得"这是程序员的东西，跟我没关系"，直接退场。文章的目标读者是普通人，不是开发者。
